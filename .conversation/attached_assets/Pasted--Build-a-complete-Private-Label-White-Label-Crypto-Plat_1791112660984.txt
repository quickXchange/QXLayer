
Build a complete Private Label / White Label Crypto Platform that allows us to create and manage branded crypto products for multiple clients from one central system.

The platform should be modular, scalable, secure, and designed so new services can be added later without rebuilding the core system.

1. Main Concept

Create a central Super Admin Platform where we can create a new client/brand and choose which crypto products are enabled for that client.

Each client must have their own:

- Brand name
- Logo
- Domain / custom domain
- Colors and theme
- Dark / Light mode
- Languages
- Supported cryptocurrencies
- Supported blockchain networks
- Payment methods
- Fees and pricing
- Deposit addresses
- API integrations
- Telegram configuration
- Customers
- Orders
- Analytics
- Email configuration
- Legal pages
- Support information

All clients must be isolated from each other.

Use a proper multi-tenant architecture.

3. Crypto Payment Gateway

Create a private-label crypto payment gateway.

Businesses should be able to accept crypto payments through:

- Hosted checkout
- Payment links
- QR codes
- API
- Webhooks
- Telegram
- Website integration

Support multiple blockchain networks and tokens.

Payment flow:

Merchant creates invoice → customer chooses crypto/network → unique payment information is generated → blockchain payment is monitored → confirmations are tracked → invoice status updates automatically → webhook is sent to merchant.

Statuses should include:

Pending
Waiting for Payment
Payment Detected
Confirming
Paid
Expired
Underpaid
Overpaid
Failed
Refunded

Merchant dashboard should show:

- Payments
- Transactions
- Invoices
- Customers
- Balances
- Settlements
- Refunds
- API keys
- Webhooks
- Payment links
- Analytics

9. Blockchain Engine

Build the architecture so blockchain providers are replaceable.

Each network can have:

Primary Provider
Secondary Provider
Manual Fallback

Example:

Ethereum → Alchemy
BSC → Alchemy
TRON → TRON provider
Bitcoin → Bitcoin node/provider
Solana → Solana RPC

Never hardcode one provider into the business logic.

If the primary provider fails, the system should safely switch to the configured fallback where supported.

Track:

- latest block
- deposits
- confirmations
- transaction hash
- amount
- token contract
- address
- memo/tag where required
- provider health
- synchronization status

12. Security

Security is critical.

Implement:

- Tenant isolation
- Owner/Admin roles
- Staff permissions
- 2FA
- secure sessions
- API key hashing
- webhook signature verification
- rate limiting
- audit logs
- login history
- suspicious activity monitoring
- encrypted sensitive configuration
- CSRF/XSS protections
- secure file uploads
- sanitized SVG uploads

Never expose private keys, API secrets or provider credentials to the frontend.

15. Important Architecture Rule

Do NOT build everything as one giant application with duplicated logic.

Use shared services for:

Authentication
Pricing
Orders
Payments
Blockchain monitoring
Wallets
Notifications
Brand configuration
API integrations

Website, Telegram Bot, Telegram Mini App and future mobile apps should consume the same backend services.

The final architecture should be:

PRIVATE LABEL CORE

→ Exchange Engine
→ Crypto Payment Engine
→ Blockchain Engine
→ Wallet Engine
→ Pricing Engine
→ Merchant API
→ Website
→ Telegram Bot
→ Telegram Mini App
→ Future Mobile Apps

Before implementing major changes, first inspect the existing project and reuse working infrastructure where possible.

Do not break existing Exchange/Swap/Convert functionality.

First produce the proposed architecture, database changes, tenant-isolation strategy, module structure, and implementation phases.
