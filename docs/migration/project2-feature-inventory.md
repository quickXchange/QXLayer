# Project 2 feature inventory and migration map

Current source was inspected, not just the visible UI. Older `docs/foundation.md` describes an earlier foundation and is not authoritative for subsequently implemented features.

**Status:** implemented = functional configuration/workflow; sandbox = simulated only; prepared = contracts/configuration without execution.  
**Decisions:** COPY = portable pure utility; ADAPT = preserve behavior with target namespaces/security; MERGE = use target capability through a tenant-aware boundary; REBUILD = new infrastructure not already implemented; REPLACE = only a source integration seam, never an existing Project 1 engine.

## Hidden relationships and enforcement

- Tenant membership is checked before scoped service access. Private delivery gates add customer ownership and provisioning checks.
- Request attachments/events without a direct `tenant_id` are scoped through request/owner relationships. An unaffiliated account must never attach or retrieve another owner's file.
- Catalogs/plans/definitions are platform-wide; tenant assignments/overrides/subscriptions are tenant-local. `tenants` itself is identified by its primary key.
- Compound foreign keys bind order→pricing and wallet→tenant asset selection. Recreate these in the new schema; do not weaken them to single-ID lookups.
- Source runtime transaction settings are contextual, **not a data filter**. Preserve authorization and tenant predicates in each service query.
- Product execution and a platform billing integration are not supplied by source configuration forms.
