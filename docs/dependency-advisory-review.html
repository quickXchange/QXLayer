1. braces

Installed: braces 3.0.3. Advisory: GHSA-vfj7-8cjw-p6xm / CVE-2026-93687, high severity.

Deeply nested brace patterns can overflow recursive AST walkers during compilation/expansion. This is different from a URL or file name containing braces: those strings become vulnerable only if supplied as patterns to the affected functions.

Exact dependency paths

@workspace/api-server
  → http-proxy-middleware 4.2.0
    → micromatch 4.0.8
      → braces 3.0.3

@workspace/mockup-sandbox (development dependency)
  → fast-glob 3.3.3
    → micromatch 4.0.8
      → braces 3.0.3

Exposure

  • The Clerk proxy uses a static options object with no pathFilter, router or spread configuration. The installed proxy library defaults pathFilter to the plain string /.
  • The plain-string branch uses URL parsing and prefix comparison, not micromatch/braces. A request cannot supply a proxy filter through its URL, query, headers or body.
  • Path rewriting removes the fixed /api/__clerk prefix with a developer-defined regular expression; the request is not a glob pattern.
  • Preview discovery calls fast-glob with the constant pattern src/components/mockups/**/*.tsx and constant ignore patterns. HTTP requests can trigger a rescan, but do not supply or modify those patterns. Customer uploads go to private object storage, not the source directory.

Verification and smallest safe remedy

A new development-only check parses the proxy options and verifies the constant preview pattern. It instruments the installed braces module and calls the actual proxy filter with normal, deeply nested, encoded and query-string URL inputs. All four inputs remained on the plain-path branch; there were zero brace-parser calls.

Public npm registry metadata confirms braces 3.0.3, micromatch 4.0.8, http-proxy-middleware 4.2.0 and fast-glob 3.3.3 are their latest releases. There is no patched release to install. No replacement matcher, dependency downgrade, local fork or scanner suppression was introduced.

Disposition: NOT EXPLOITABLE from untrusted customer input in the reviewed code. The package defect remains. Reassess if any code starts accepting user-defined glob/brace patterns or dynamic proxy filters.

2. uuid

Installed: uuid 9.0.1. Advisory: GHSA-w5hq-g745-h8pq / CVE-2026-41907 and CVE-2026-41988, high severity.

The affected functions are v3(), v5() and v6() when callers provide insufficient output buffers or invalid offsets. The advisory explicitly excludes v4(). Version 9 does not export v6(); its relevant affected functions are v3()/v5().

Exact private-file dependency paths

@workspace/api-server → @google-cloud/storage 8.2.0
  ├─ gaxios 6.7.1 → uuid 9.0.1
  └─ google-auth-library 9.15.1
     ├─ gaxios 6.7.1 → uuid 9.0.1
     ├─ gcp-metadata 6.1.1 → gaxios 6.7.1 → uuid 9.0.1
     └─ gtoken 7.1.0 → gaxios 6.7.1 → uuid 9.0.1

Exposure

  • All four paths resolve to the same installed gaxios module. Its only uuid call is v4() to generate an internal multipart boundary. It passes no caller-provided buffer, offset or options.
  • Private attachment IDs and object keys use Node's crypto.randomUUID(), not the vulnerable npm uuid functions.
  • No application call to npm uuid v3()/v5()/v6(), and no upload field mapped to a UUID output buffer or offset, was found.
  • The existing storage credentials, upload/download implementation, ownership filters and file-response protections were left unchanged.

Verification and smallest safe remedy

The new check inspects the actual installed gaxios source and instruments uuid exports. It exercises the real multipart serializer with a no-network adapter. The serializer generated one valid boundary via v4() with zero arguments; there were zero affected-function calls.

The scanner's first fixed release is uuid 11.1.1, outside gaxios 6.7.1's supported ^9.0.1 range. Registry metadata confirms gaxios 6.7.1 and google-auth-library 9.15.1 are the latest compatible releases, and @google-cloud/storage 8.2.0 is the latest SDK. That SDK still specifies gaxios ^6.0.2 and google-auth-library ^9.6.3.

Newer gaxios/auth major versions exist, but forcing them under the current Storage SDK would cross its declared compatibility ranges and alter the HTTP/authentication chain. No major override or SDK replacement was applied merely to clear the scanner.

Disposition: NOT EXPLOITABLE through the reviewed private-file chain. The library vulnerability remains installed. Reassess if consumers introduce name-based UUIDs or caller-provided UUID buffers/offsets.
