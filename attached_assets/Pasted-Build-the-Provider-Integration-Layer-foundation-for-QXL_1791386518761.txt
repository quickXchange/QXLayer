Build the Provider Integration Layer foundation for QXLayer in DEVELOPMENT ONLY.

The White Label Exchange core flow is now verified end-to-end.

The next goal is to create a clean, scalable provider architecture so real providers can be integrated later without hardcoding them into the Exchange, Routes, tenants or UI.

IMPORTANT:
This phase is ARCHITECTURE + ADMIN CONFIGURATION ONLY.

Do NOT connect any real external provider/API yet.
Do NOT request or use real API keys.
Do NOT create wallets or deposit addresses.
Do NOT execute blockchain transactions.
Do NOT move funds.
Do NOT publish.
Do NOT modify Production, DNS or Production SQL.

--------------------------------------------------
1. PROVIDER CATALOG
--------------------------------------------------

Create/complete a central Provider Catalog controlled by Super Admin.

Each provider should support:

- Provider ID
- Name
- Logo
- Description
- Category
- Supported services
- Status
- Environment support
- Credential schema
- Configuration schema
- Capability metadata
- Created/updated timestamps

Provider categories must be extensible.

Initial categories:

- Exchange / Convert
- Payment
- Rates / Market Data
- RPC / Blockchain Node
- Deposit / Wallet Infrastructure
- Webhook / Event Provider

Do not assume one provider belongs to only one category.

A provider may support multiple capabilities.

--------------------------------------------------
2. PROVIDER STATUS
--------------------------------------------------

Use explicit statuses such as:

Coming Soon
Configuration Only
Available
Disabled

Connection state must be separate:

Not Configured

Only a real implemented adapter with a successful connection verification may later become Connected.

Since this phase has no real integrations, providers must remain Not Configured / Configuration Only as appropriate.

--------------------------------------------------
3. ADAPTER ARCHITECTURE
--------------------------------------------------

Create a reusable provider adapter/interface architecture.

The Exchange core must NOT call provider-specific code directly.

Use a structure conceptually similar to:

Exchange Core
→ Provider Service
→ Provider Adapter
→ External Provider

Prepare capability interfaces for future implementations such as:

Rates:
- getRate()
- getMarkets()

Convert:
- getQuote()
- createConversion()
- getConversionStatus()

Payments:
- createPayment()
- getPaymentStatus()

Deposits:
- createDepositAddress()
- getDepositStatus()

RPC:
- getBlockHeight()
- getTransaction()
- getTransactionStatus()

Webhooks:
- verifyWebhook()
- normalizeWebhookEvent()

These are capability contracts only.

Do NOT implement fake successful provider calls.

Unsupported capabilities must explicitly return unsupported/not implemented.

6. PROVIDER CREDENTIAL SECURITY
--------------------------------------------------

Prepare secure credential handling.

Future credentials may include:

API Key
API Secret
Webhook Secret
Account ID
RPC URL
Other provider-specific secrets

Requirements:

- Never expose secrets in frontend responses.
- Never include secrets in logs.
- Never include secrets in audit payloads.
- Never return full secret values after save.
- UI should show masked state only.
- Keep credentials isolated by tenant/provider/environment.
- Super Admin must not accidentally expose customer credentials.

Use the project's existing secure secret/encryption approach where available.

If secure encrypted credential persistence does not currently exist, build the interface/storage boundary safely but do NOT invent weak encryption.

Report this clearly.
