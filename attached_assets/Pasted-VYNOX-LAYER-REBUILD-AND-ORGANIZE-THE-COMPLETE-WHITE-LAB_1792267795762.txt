3. COMPLETELY REBUILD PRICING RULE LOGIC

THIS IS THE MOST IMPORTANT FUNCTIONAL REQUIREMENT.

Pricing Rules must be directional and support the ANY wildcard.

Example A:

SOURCE: ANY ELIGIBLE CRYPTO
TARGET: EUR FIAT PAYMENT METHODS
FEE: 1%

This is ONE rule:

ANY → EUR = 1%

It should automatically apply to compatible configured routes such as:

- USDT TRC20 → SEPA EUR
- BTC Bitcoin → Revolut EUR
- ETH ERC20 → N26 EUR
- USDC ERC20 → Wise EUR

Do NOT create a separate pricing rule for each crypto asset.

The wildcard must match eligible crypto assets/networks only, with compatible and enabled EUR payment methods and available market rates.

Example B:

SOURCE: EUR FIAT PAYMENT METHODS
TARGET: ANY ELIGIBLE CRYPTO
FEE: 1%

EUR → ANY = 1%

This is a SEPARATE reverse-direction rule with independently configurable pricing, fees, limits and priority.

Example C:

SOURCE: USDT TRC20
TARGET: SEPA EUR
FEE: 0.5%

This more specific rule can override the generic ANY → EUR rule for that exact compatible pair.

Support the following rule types:

- Any Crypto → Any Fiat
- Any Crypto → Specific Fiat Currency
- Specific Crypto Asset → Fiat Currency
- Specific Crypto Asset + Network → Specific Payment Method
- Specific Fiat Currency → Any Crypto
- Specific Payment Method → Specific Crypto Asset + Network
- Other explicitly valid Crypto ↔ Fiat combinations

Support:

- Direction
- Source and destination matching
- Any wildcard
- Specific-rule precedence over general fallback
- Deterministic priority
- Enabled / Disabled / Blocked states
- Automatic market-based rates
- Manual exchange rates
- Percentage spreads and fees
- Fixed fees
- Minimum and maximum amounts
- Optional route restrictions

Do not apply fees twice, confuse markup with commission or invert rates incorrectly.

Provide clear mathematical calculations for both directions.

Avoid conflicting rules and show which exact rule matched a quote.
